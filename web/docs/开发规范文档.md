# 智云实验室 Web 端开发规范文档

## 1. 文档目标

本文档用于统一 Web 前端团队的开发方式、代码风格、目录组织、协作流程和质量标准，降低多人协作成本，提升代码可维护性与交付稳定性。

适用范围：

- 智云实验室 Web 前端工程。
- Vue 3 单文件组件开发。
- Vite 本地开发、构建与预览流程。
- 页面、组件、样式、资源、接口和发布相关规范。

## 3. 环境与依赖规范

### 3.1 Node.js 与包管理

- 统一使用 npm 管理依赖。
- 新增、删除或升级依赖后必须同步提交 `package.json` 与 `package-lock.json`。
- 禁止混用 `npm`、`yarn`、`pnpm`，避免生成多个锁文件。
- 建议团队统一 Node.js LTS 版本，并在后续补充 `.nvmrc` 或 Volta 配置。

### 3.2 常用命令

| 场景 | 命令 |
| --- | --- |
| 安装依赖 | `npm install` |
| 本地开发 | `npm run dev` |
| 生产构建 | `npm run build` |
| 本地预览构建结果 | `npm run preview` |

### 3.3 依赖引入原则

- 优先使用 Vue 官方生态和维护活跃的依赖。
- 引入新依赖前需评估包体积、维护状态、许可证和替代方案。
- 工具类函数优先自行封装项目内通用方法，避免为少量功能引入大型依赖。
- 若后续启用路由，建议统一使用 Vue 官方路由方案 `vue-router`，并清理无业务用途的依赖。

当前目录结构：

```text
web/

    api/
    assets/
    components/
      module/
    composables/
    constants/
    router/
    views/
      dashboard/
      devices/

      statistics/
      system/
    App.vue
    main.js
    style.css
  docs/
  index.html
  package.json
  package-lock.json
  vite.config.js
```

推荐后续业务扩展目录：

```text
src/
  api/             # 接口请求与接口模块
  assets/          # 图片、字体、SVG 等静态资源
  components/      # 可复用基础组件和业务组件
  composables/     # Vue 组合式函数
  constants/       # 常量、枚举和配置
  views/           # 路由页面、布局和占位视图组件，按模块建文件夹
  router/          # 路由配置
  stores/          # 状态管理
  styles/          # 全局样式、变量、重置样式
  utils/           # 通用工具函数
  App.vue
  main.js
```

目录使用要求：

- 当前项目路由页面和布局统一放入 `src/views/`，并按模块建立独立文件夹，例如 `dashboard/`、`room-control/`、`layout/`。
- 与业务强绑定的子组件优先放在对应模块目录下的 `components/` 文件夹，例如 `src/views/dashboard/components/`，避免子组件散落。
- 可跨 2 个以上模块复用的通用组件再放入 `src/components/`。
- 可被 2 个以上页面复用的逻辑再抽取到 `components/`、`composables/` 或 `utils/`。
- 静态图片、图标、字体等资源统一放入 `src/assets/` 或 `public/`。
- 需要经 Vite 处理、打包和哈希化的资源放入 `src/assets/`。
- 需要原路径访问的资源放入 `public/`。

## 5. 命名规范

| 类型 | 规范 | 示例 |
| --- | --- | --- |
| Vue 组件文件 | PascalCase | `LabDashboard.vue` |
| 页面组件文件 | PascalCase | `DeviceMonitor.vue` |
| 组合式函数 | camelCase，使用 `use` 前缀 | `useLabDevices.js` |
| 工具函数文件 | camelCase 或 kebab-case | `formatDate.js` |
| 常量 | UPPER_SNAKE_CASE | `DEVICE_STATUS_MAP` |
| CSS class | kebab-case | `lab-card` |
| 事件名 | kebab-case | `submit-form` |
| 变量与函数 | camelCase | `deviceList` |

命名要求：

- 名称应表达业务含义，避免 `data`、`list`、`item` 等过宽泛命名。
- 布尔变量建议使用 `is`、`has`、`can`、`should` 前缀。
- 事件处理函数建议使用 `handle` 前缀，例如 `handleSubmit`。
- 接口请求函数建议使用动作和资源组合，例如 `fetchLabList`、`updateDeviceStatus`。

## 6. Vue 组件开发规范

### 6.1 单文件组件结构

统一使用 Vue 3 `<script setup>` 写法。

推荐顺序：

```vue
<script setup>
import { ref } from 'vue'
</script>

<template>
  <section class="example-card">
    示例内容
  </section>
</template>

<style scoped>
.example-card {
  padding: 16px;
}
</style>
```

组件要求：

- 一个组件只负责一个清晰职责。
- 组件 props 和 emit 应命名清晰，避免隐式依赖父组件数据结构。
- 页面组件负责数据组织和业务流程，基础组件负责展示和交互。
- 复杂逻辑应抽取为 `composables`，避免组件文件过长。
- 模板中避免写复杂表达式，复杂计算放入计算属性或函数。
- 不直接修改 props，使用 emit 通知父组件更新。

### 6.2 Props 与 Emits

推荐写法：

```js
const props = defineProps({
  deviceId: {
    type: String,
    required: true,
  },
})

const emit = defineEmits(['refresh', 'update-status'])
```

约定：

- props 必须声明类型。
- 必填字段使用 `required: true`。
- emit 事件名使用 kebab-case。
- 复杂对象 props 应提供结构说明或拆分为更明确字段。

### 6.3 状态与副作用

- 局部状态使用 `ref` 或 `reactive`。
- 派生状态使用 `computed`。
- 副作用逻辑使用 `watch` 或 `watchEffect`，并控制触发范围。
- 异步请求需要处理 loading、error 和 empty 状态。
- 定时器、事件监听、订阅等副作用需要在组件卸载时清理。

## 7. JavaScript 编码规范

### 7.1 基础规则

- 使用 ES Module 语法。
- 优先使用 `const`，需要重新赋值时再使用 `let`。
- 禁止使用 `var`。
- 使用单引号，与当前项目代码保持一致。
- 语句末尾不强制分号，与当前项目代码保持一致。
- 函数应保持短小，单个函数只处理一个主要任务。
- 不在业务代码中保留 `console.log`，调试完成后应删除。

### 7.2 异步处理

- 接口请求统一使用 `async` / `await`。
- 异步函数必须处理异常。
- 用户可感知的异常需要给出明确提示。
- 重试、轮询和并发请求应设置边界，避免无限请求。

示例：

```js
async function loadDeviceList() {
  try {
    const devices = await fetchDeviceList()
    return devices
  } catch (error) {
    console.error('加载设备列表失败', error)
    return []
  }
}
```

### 7.3 注释规范

- 优先通过清晰命名表达意图。
- 只为复杂业务规则、边界条件和非显而易见的实现添加注释。
- 注释应解释原因，而不是重复代码行为。
- 废弃代码必须删除，不使用大段注释保留。

## 8. 样式规范

### 8.1 全局样式

- 全局样式入口当前为 `src/style.css`。
- 全局 CSS 变量统一放在 `:root`。
- 颜色、字体、阴影、间距等设计令牌应优先使用 CSS 变量。
- 页面或组件私有样式优先使用组件内 `<style scoped>`。
- 跨页面复用的样式再抽取到 `src/styles/`。

### 8.2 CSS 编写规则

- class 使用 kebab-case。
- 避免过深选择器，建议不超过 3 层。
- 避免依赖元素选择器覆盖组件样式。
- 响应式断点应集中维护，避免任意散落。
- 颜色值优先使用变量，避免重复硬编码。
- 对可交互元素补充 `hover`、`focus-visible` 和禁用状态。

### 8.3 响应式与可访问性

- 页面必须兼容桌面端和移动端。
- 图片必须提供有意义的 `alt`；装饰图片使用空 `alt=""`。
- 按钮使用 `button` 元素，链接跳转使用 `a` 元素。
- 图标若仅用于装饰，应设置 `aria-hidden="true"`。
- 表单项需要具备可识别标签和错误提示。
- 颜色对比度应满足基础可读性要求。

## 9. 静态资源规范

- 图片资源按业务模块或类型分类存放。
- SVG 图标优先作为组件或 sprite 统一管理。
- 大图应压缩后再提交，避免影响仓库体积和页面加载速度。
- 文件名使用小写 kebab-case，例如 `lab-device-empty.png`。
- 无业务使用的模板资源应及时清理。

## 10. 接口与数据规范

当前项目已建立基础接口层，首页概览数据封装在 `src/api/dashboard.js`，模拟数据和业务常量分别放在 `src/constants/`。后续接入真实后端时继续遵循以下要求：

- 所有请求封装在 `src/api/`。
- 接口地址、超时时间和通用 headers 统一配置。
- 业务组件不直接拼接请求地址。
- 接口函数只负责请求和基础数据转换，不混入页面展示逻辑。
- 后端返回数据进入页面前应做空值和异常结构兜底。
- 涉及鉴权、租户、实验室 ID 等上下文信息时统一由请求层注入。

推荐结构：

```text
src/api/
  client.js
  lab.js
  device.js
  user.js
```

## 11. 路由与状态管理规范

当前项目已配置 Vue Router，路由文件位于 `src/router/index.js`；尚未引入状态管理库。现有路由结构如下：

```text
/login          # 登录
/
  redirect: /dashboard
/dashboard       # 首页概览
/labs            # 实验室管理
/devices         # 设备管理
/room-control    # 机房综合管控
/reservations    # 预约管理
/repairs         # 报修管理
/records         # 使用记录
/statistics      # 数据统计
/system          # 系统设置
```

路由与状态管理扩展建议：

- 路由统一放在 `src/router/`。
- 路由组件统一放在 `src/views/`，并按模块拆分子目录。
- 路由 path 使用 kebab-case。
- 需要权限控制的路由在路由元信息中声明。
- 全局状态仅保存跨页面共享的数据。
- 页面局部数据优先保留在页面组件或 composable 中。
- 状态管理库引入前需要确认是否确有跨页面共享和调试需求。

## 12. 质量检查规范

### 12.1 提交前检查

每次提交前至少执行：

```bash
npm run build
```

检查目标：

- 生产构建通过。
- 页面无明显运行时报错。
- 新增页面在桌面端和移动端基础可用。
- 不提交调试日志、临时文件和无用资源。

### 12.2 后续建议补齐

当前项目尚未配置自动化质量工具，建议后续补充：

| 工具 | 目的 |
| --- | --- |
| ESLint | JavaScript 与 Vue 代码质量检查 |
| Prettier | 统一格式化 |
| Vitest | 单元测试 |
| Vue Test Utils | 组件测试 |
| Playwright | 关键流程端到端测试 |
| husky + lint-staged | 提交前自动检查 |

### 12.3 测试要求

- 工具函数应优先补充单元测试。
- 复杂组件应覆盖关键交互和异常状态。
- 重要业务流程应补充端到端测试。
- 修复缺陷时建议补充回归测试。

## 14. 安全与配置规范

- 禁止将账号、密码、Token、密钥等敏感信息提交到仓库。
- 环境变量文件应按环境区分，例如 `.env.development`、`.env.production`。
- 公开给前端的环境变量需确认不包含敏感信息。
- 用户输入展示前需要考虑 XSS 风险。
- 外链使用 `target="_blank"` 时建议同时设置 `rel="noopener noreferrer"`。
- 文件上传、下载、实验室设备控制等敏感操作需进行权限校验和二次确认。

## 15. 发布规范

发布前检查：

- 依赖安装成功。
- `npm run build` 执行成功。
- 关键页面可正常访问。
- 接口环境指向正确。
- 静态资源加载正常。
- 浏览器控制台无阻塞级错误。
- 版本说明或变更记录已同步。

推荐发布流程：

```text
拉取最新代码
安装依赖
执行构建
验证构建产物
部署到测试环境
完成业务验收
部署到生产环境
线上回归验证
```

## 16. 代码评审清单

评审时重点关注：

- 功能是否满足需求。
- 是否存在空状态、错误状态和加载状态。
- 是否引入重复代码或过度抽象。
- 组件职责是否清晰。
- 命名是否表达业务语义。
- 样式是否影响其他页面。
- 是否存在明显性能问题。
- 是否有敏感信息泄露风险。
- 是否补充必要测试或手动验证说明。
- 是否通过 `npm run build`。

| 低 | 建立自动化 CI 构建和发布流水线 |

## 18. 执行原则

- 先保证一致性，再追求个性化实现。
- 先保证可读性，再追求技巧性写法。
- 先保证业务正确，再做性能优化。
- 先小步提交，再集中集成。
- 所有规范应服务于交付效率和代码质量，如与实际业务冲突，应在团队内确认后更新本文档。
